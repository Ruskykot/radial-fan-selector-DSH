# Ввод/вывод через интерактивный React-артефакт (вместо чат-диалога)

Статус: **предложение / не реализовано**. Исправленная версия: артефакт делается на
**React**, а не на Rust→WASM. Документ заменяет ранее ошибочный анализ
`ARTIFACT_WASM.md`. Код не менялся.

---

## 1. Резюме (исправлено)

Текущий ввод/вывод — **диалог**: агент спрашивает `q_req`/`p_req`/фильтры через
`ask_user_question`, затем вызывает Python-ядро и печатает таблицу + PNG в чат.
Альтернатива — **артефакт на React**: самодостаточный виджет (форма слева,
результаты и график справа) в панели харнесса.

Коррекция «Rust → React» меняет суть решения радикально и **в лучшую сторону**:

- React — это **только слой UI**. Расчёт **не переносится** в браузер как отдельная
  реализация, он остаётся в Python-ядре (единственный источник истины).
- Исчезают две главные проблемы Rust→WASM-варианта: **вторая реализация ядра** и
  **числовая паритетность** МНК (`np.polyfit` vs порт).
- Артефакт становится **тонким клиентом** API-слоя из `MCP.md`.

Рекомендация — **тонкий React-клиент поверх MCP/HTTP** (раздел 5–6).

---

## 2. Текущий поток ввода/вывода (чат-диалог)

```
Пользователь: «нужен вентилятор на 7500 м³/ч и 700 Па»
  → агент: ask_user_question «уточните Q и P»        (раунд 1)
  → агент: ask_user_question «тип давления?»          (раунд 2)
  → агент: (опц.) multi_select фильтры                (раунд 3)
  → агент: run_selection(...) → dict
  → агент: печатает таблицу + chart.png → изображение
```

2–4 раунд-трипа через LLM; поля ввода и вывода размазаны по чату.

Q 100–100 000, P 10–10 000) показывается в форме до запроса.

## 4. Ключевое следствие «React, а не Rust»

React отвечает только за **presentation + I/O**. Вся механика (`core.py`,
`selector.py`, данные) остаётся в Python и вызывается через API. Поэтому:

- **одна реализация ядра** (Python) — нет дрейфа версий;
- **нет числовой паритетности** — считает тот же код, что и `golden`;
- порт нужен ровно нулевой — React-виджет читает `result.schema.json` как контракт.

Остаётся только выбрать, **откуда** React-виджет берёт данные (раздел 5).

## 5. Три стратегии вычисления в React-артефакте

| Стратегия | Где расчёт | Плюсы | Минусы | Вердикт |
|-----------|-----------|-------|--------|---------|
| **(a) Тонкий клиент → API** | Python-сервер (MCP/HTTP) | одно ядро, ноль порта, пары с MCP.md | нужен запущенный сервер + сеть из браузера | **рекомендовано** |
| (b) Pyodide (Python в браузере) | тот же Python-код + numpy, скомпилированный в WASM | самодостаточно, одна реализация, полная паритетность «бесплатно» | тяжёлый пейлоад (~10–20 МБ), медленный первый старт | фолбэк «офлайн без порта» |
| (c) TS-порт ядра | переписанный core на TypeScript | клиентски без сервера | вторая реализация + риск паритетности (тот же, что был у Rust) | не рекомендовано |

**Почему (a), а не (c).** Коррекция на React убирает сам повод портировать ядро:
нужды в клиентском расчёте больше нет — есть API-слой (MCP). Порт в TS вернул бы
ровно ту проблему «двух реализаций», которую Rust→WASM-вариант вносил в
`SYNTHESIS.md` и которую мы теперь сняли.

**Про (b).** Если когда-то потребуется «полностью офлайн/без сервера», Pyodide
позволяет запустить *буквально тот же* `fan_selector` + numpy в браузере без
порта — это отдельное решение, не часть основного пути.

## 6. Рекомендуемая стратегия: тонкий React-клиент поверх MCP

React-артефакт выступает **MCP-клиентом** для сервера из `MCP.md`:

```
React-артефакт (браузер) ── Streamable HTTP ──▶ MCP-сервер ──▶ run_selection
        (форма/таблица/график)                 (select_fan / catalog / chart)
```

- инструмент `select_fan` → заполняет форму и возвращает `fan-result/v1`;
- инструмент `fan_chart` → возвращает PNG/base64, либо сервер отдаёт `curve`-данные
  из результата, и **React сам рисует SVG** (рекомендуется — векторный, чёткий,
  кириллица шрифтами браузера);
- ресурсы `fan://data/*` → подгрузка справочников для выпадающих списков фильтров.

**Прагматичный фолбэк.** Если браузерный MCP окажется тяжёлым (CORS/сессии/auth),
поднять тонкий JSON-эндпоинт (FastAPI) поверх того же `run_selection`, а MCP
оставить для не-браузерных клиентов. Контракт один (`result.schema.json`), так что
React-виджет не заметит разницы.

## 7. Стек и график

| Слой | Выбор |
|------|-------|
| UI | React + TypeScript + Vite |
| Состояние формы | `useState`/`useReducer` (или React Hook Form) |
| Таблица | обычный компонент; строки из `results[]` |
| График | SVG: ручной (d3-shape) или Recharts; кривые P(Q) + сеть P=kQ² + рабочая точка + легенда |
| Валидация | зеркало `config.json::validation` клиентски, ошибка до запроса |
| Данные/контракт | `result.schema.json` как тип ответа; `selection.schema.json` как модель формы |

График рисовать в React проще, чем в Pillow: SVG-текст наследует шрифты браузера
(кириллица бесплатно), масштабируется без потерь и интерактивен (тултипы).

## 8. Сравнение: чат-диалог vs React-артефакт

| Критерий | Чат-диалог (навык) | React-артефакт |
|----------|--------------------|----------------|
| Раунд-трипы | 2–4 через LLM | 0 — всё в виджете |
| Задержка | секунды (агент + Python) | миллисекунды на UI + один HTTP-запрос |
| Валидация входа | на совести агента | в форме, по `validation.*` |
| Расчёт | Python-ядро | **то же Python-ядро** (через API) |
| Кодовая база | Python-ядро | Python-ядро + тонкий React-UI |
| График | PNG (Pillow) | SVG (векторный) |
| Инфраструктура | есть | сервер (MCP/HTTP) + встраивание в DSH |

## 9. Связь с MCP.md

Артефакт — это **UI-клиент** того самого MCP-сервера. Вместе получается цепочка
«одно ядро → один API → один UI»:

```
        Python-ядро (core.py)            ── единственный источник истины
             │
        MCP-сервер (API)                 ── docs/archive/MCP.md
             │  Streamable HTTP
        React-артефакт (UI)              ── этот документ
```

MCP обслуживает и React-артефакт, и любой другой клиент (CLI, сторонние агенты) —
один API вместо трёх адаптеров с дублирующей логикой.

## 10. План (по фазам)

1. **Фаза 1 — API.** Поднять MCP-сервер поверх Python-ядра (`docs/archive/MCP.md`, фаза 1).
   Это обязательная предпосылка: React-артефакт не имеет смысла без API.
2. **Фаза 2 — React-виджет.** Форма (Q/P/тип/фильтры) + таблица + SVG-график,
   данные из `select_fan`/`fan_chart`. Собрать самодостаточный билд.
3. **Фаза 3 — встраивание в DSH.** Подключить артефакт через механизм харнесса
   (клиент-плагин / HTML-артефакт). **Только после подтверждения** (раздел 11).
4. **(Опц.) Фаза 4 — офлайн.** Вариант Pyodide, если потребуется работа без сервера.

---

## 11. Открытые вопросы (блокеры)

1. **Механизм артефакта в DSH.** Как харнесс рендерит сторонний HTML/JS-виджет в
   панели (client-plugin / iframe / React-artifact) и как туда попадает билд.
   Если DSH-артефакты — это React/TSX (по образцу Claude Artifacts), совместимость
   с Vite-шеллом надо подтвердить.

2. **Доступ React-артефакта к MCP-серверу.** Браузерный MCP по Streamable HTTP
   (CORS/сессии/auth) — работает ли в DSH, или нужен тонкий REST-фолбэк (раздел 6).

3. **Судьба `config.py`.** Для UI достаточно границ `validation.*` и `top_n`; живой
   конфиг не обязателен — зашитые константы, версионируемые с релизом.

| Что | Статус |
|-----|--------|

## 13. Итог одной строкой

React-артефакт — это **тонкий UI-клиент** над существующим Python-ядром (через
MCP/HTTP): расчёт не портируется, вторая реализация не нужна, паритетность не
нужна; остаются только вопросы встраивания виджета в DSH и доступа браузера к API.
