# Бизнес-логика как MCP-сервер (вместо навыка)

Статус: **предложение / не реализовано**. Документ отвечает на вопрос «стоит ли
оформлять расчётное ядро и механику подбора как **MCP** (Model Context Protocol),
а не как DSH-навык, и как именно». Код не менялся; это проектировочное решение.

---

## 1. Резюме

Расчётное ядро уже имеет ровно ту форму, которую требует MCP-сервер: **JSON-in /
JSON-out без интерфейса**. Поэтому «оформить как MCP» — это не переписывание
бизнес-логики, а добавление **тонкого адаптера** поверх уже существующего шва.

Рекомендация — **аддитивно, тремя уровнями**:

1. **Сейчас (без риска):** добавить MCP-сервер как новый адаптер, ядро не трогать.
   Навык оставить как фолбэк/UX-обёртку.
2. **Когда хост (DeepSeek Harness) подтвердит потребление MCP:** навык
   превращается в тонкий указатель «вызови инструменты MCP `fan-selector`».
3. **Конечное состояние:** MCP-сервер — единственный машиночитаемый контракт
   бизнес-логики; навык либо удалён, либо остался как человекопонятная обёртка.

**Ключевой открытый вопрос** (раздел 7): потребляет ли DeepSeek Harness MCP-серверы
как инструменты? Пока это не подтверждено, полностью заменять навык на MCP нельзя —
но MCP-сервер ценен независимо: он делает логику переносимой в любой MCP-клиент
(Claude Desktop, Cursor, VS Code, кастомные приложения, другие агенты).

## 2. Текущая архитектура (термины codebase-design)

| Понятие | Что это в проекте |
|---------|-------------------|
| **Модуль** | `fan_selector.select` — функции `run_selection`, `catalog_lookup`, `chart_selection` |
| **Интерфейс** | один `dict` на вход, один `dict` на выход; ошибки — полем `{"error": ...}`, исключения наружу не бросаются |
| **Реализация (глубокая)** | валидация (`config.py`), загрузка данных (`repositories.py`), МНК-аппроксимация, статическое давление, КПД, мощность, коэффициент запаса, подбор двигателя, сортировка (`core.py`, `selector.py`) |
| **Шов** | точка входа `run_selection(dict) -> dict` |
| **Адаптеры, уже сидящие на шве** | (1) CLI `__main__.py`, (2) DSH-навык `.dsh/skills/fan-selector/SKILL.md`, (3) тесты `tests/test_golden.py` |

Модуль — **глубокий**: крошечный интерфейс (`{q_req, p_req, ...} → результат`)
за которым спрятана вся механика 66 вентиляторов × полиномы × двигатели.
**Deletion-test**: удали ядро — и вся механика расчёта всплывёт заново в каждом
адаптере. Это и есть идеальная предпосылка для MCP.

Доказательство, что шов уже «спроектирован под MCP»: docstring `select.py` сам
перечисляет рантаймы — *«CLI, subprocess, MCP, тесты, инструмент харнесса»*.
В `REDESIGN.md` среди удалённого значится `github-mcp/` — то есть MCP-подход уже
рассматривался и был отложен.

## 3. Что такое MCP и почему ядро уже готово

MCP ([modelcontextprotocol.io](https://modelcontextprotocol.io)) — открытый
стандарт, по которому приложение (сервер) предоставляет LLM-клиенту
стандартизованный интерфейс через JSON-RPC. Три примитива:

| Примитив | Роль | Аналог в fan-selector |
|----------|------|----------------------|
| **Tool** | вызываемая моделью функция с JSON-Schema на входе | `run_selection`, `catalog_lookup`, `chart_selection` |
| **Resource** | читаемые данные по URI (контекст) | `data/*.json`, `docs/CALCULATION.md`, `schema/*.json` |
| **Prompt** | переиспользуемый шаблон подсказки (опционально) | сценарий опроса Q/P из навыка |

Транспорты: **stdio** (локальный процесс) и **Streamable HTTP** (удалённый).
Для локального использования в агенте подходит stdio; для «сервера расчётов»,
к которому ходят несколько клиентов — Streamable HTTP.

Существующие артефакты, которые переносятся в MCP **1:1 без изменений**:

- `schema/selection.schema.json` → `inputSchema` инструмента `select_fan`;
- `schema/result.schema.json` → описывает возвращаемый `dict`;
- `run_selection`/`catalog_lookup`/`chart_selection` → тела инструментов;
- `data/*.json` → ресурсы.

## 4. Маппинг: функция ядра → MCP-примитив

### 4.1. Инструменты (Tools)

| Tool | Обёртка над | Вход (обязательное выделено) | Выход |
|------|-------------|------------------------------|-------|
| `select_fan` | `run_selection` | **`q_req`**, **`p_req`**, `pressure_type`, `d_reg_max`, `t_air`, `series[]`, `sizes[]`, `rpms[]` | `fan-result/v1` (summary + results[]) |
| `lookup_catalog` | `catalog_lookup` | `series[]`, `dn`, `d_over_dn` (все опциональны) | `fan-catalog/v1` (items[]) |
| `fan_chart` | `chart_selection` | **`q_req`**, **`p_req`**, `pressure_type` | `fan-chart/v1` (PNG base64) |

`fan_chart` можно сделать «умнее»: SDK MCP умеет возвращать **image-контент**, и
клиент сам отрисует PNG — тогда инструмент возвращает байты/`Image`, а не base64.
Но текущий контракт `chart_png_base64` тоже корректен и ничего не требует менять.

### 4.2. Ресурсы (Resources)

| URI | Содержимое | mimeType |
|-----|-----------|----------|
| `fan://data/fans` | `data/fans.json` | application/json |
| `fan://data/impellers` | `data/impellers.json` | application/json |
| `fan://data/motors` | `data/motors.json` | application/json |
| `fan://data/catalog` | `data/catalog.json` | application/json |
| `fan://data/config` | `data/config.json` | application/json |
| `fan://docs/calculation` | `docs/CALCULATION.md` | text/markdown |
| `fan://schema/selection` | `schema/selection.schema.json` | application/json |
| `fan://schema/result` | `schema/result.schema.json` | application/json |

Ресурсы важнее, чем кажется: они делают справочные данные **первоклассным
контекстом**, который клиент читает по запросу — без «вшивания» знаний о 66
вентиляторах в подсказку и без повторного раунд-трипа через модель.

### 4.3. Промпты (опционально)

Шаблон `подбор_вентилятора`: «Спроси Q и P → вызови `select_fan` → покажи таблицу
и график». Дублирует ветвящийся диалог навыка, поэтому его можно не добавлять:
протокол MCP и так даёт клиенту описание инструмента с параметрами. Рекомендация —
**не создавать промпты**, оставить эту роль навыку/UX хоста.

## 5. Навык vs MCP: сравнение

| Критерий | DSH-навык (сейчас) | MCP-сервер (предлагается) |
|----------|--------------------|---------------------------|
| Исполнение механики | LLM «знает» шаги и сам вызывает Python/subprocess | детерминированный вызов инструмента по схеме |
| Валидация входа | на совести агента | JSON-Schema на уровне протокола, до ядра |
| Переносимость | только внутри DSH | любой MCP-клиент |
| Версионирование контракта | текст, семвер отсутствует | `inputSchema` + версия сервера |
| Натуральноязычный ввод | агент уточняет Q/P/фильтры гибко | клиент должен заполнить обязательные поля (или его LLM делает это сам) |
| Инфраструктура | нет процесса | запущенный сервер (stdio/HTTP) |
| Зависимости | нет новых | `mcp` (Python 3.11+), опционально |
| Тестируемость end-to-end | через прогон ядра | + smoke-тест через MCP-клиент, MCP Inspector |

**Вывод:** навык силён *человеко-понятным* диалогом, MCP — *машиночитаемым*
контрактом. Это два адаптера одного и того же шва, а не конкуренты. «Как MCP, а не
как навык» корректно читать как *«сделать MCP каноническим контрактом, а навык —
вторичным UX-слоем»*.

Главный риск навыка, который снимает MCP: сейчас корректность подбора зависит от
того, **следует ли LLM шагам** (не подставит ли свои числа, не пропустит ли вызов
ядра). MCP переносит эту гарантию на протокол: плохой вход отклоняется до ядра,
результат возвращает сам сервер.

## 6. Рекомендация (три уровня, по возрастанию решительности)

1. **Аддитивно (сделать сразу).** Добавить модуль `fan_selector/mcp.py` (или
   `mcp_server/`) — тонкий адаптер над существующими функциями. Ядро и golden-тесты
   не меняются. Навык остаётся рабочим. Риск ≈ 0.

2. **Гибрид (когда хост умеет MCP).** Переписать `SKILL.md` в короткий указатель:
   «для расчёта используй инструменты MCP `select_fan` / `fan_chart` / ресурсы
   `fan://data/*`; задавай Q и P пользователю». Навык перестаёт содержать
   Python-код и подсказки о ключах результата — всё это живёт в `inputSchema`
   и ресурсах сервера.

3. **Полная замена (конечное состояние).** Удалить навык, оставить MCP-сервер
   единственной точкой входа бизнес-логики. Применимо только после подтверждения,
   что целевой хост потребляет MCP, иначе теряется рабочий сценарий в DSH.

## 7. Открытый вопрос: потребляет ли DeepSeek Harness MCP

Это **единственный блокер** для полной замены. Навык — нативный механизм
расширения DSH; MCP — внешний стандарт. Из текущей документации проекта не видно
подтверждения, что харнесс умеет монтировать MCP-сервер как набор инструментов.

Как проверить (до начала полной замены):

- уточнить у владельца харнесса поддержку MCP-клиента (stdio / HTTP) и формат
  регистрации сервера;
- если поддержки нет — реализовать и запустить сервер всё равно (ценность для
  других клиентов), а навык оставить фолбэком уровня 1.

Не утверждать «MCP вместо навыка работает в DSH», пока это не проверено.

### 8.2. Зависимость

```toml
[project.optional-dependencies]
mcp = ["mcp>=1.0"]
```

Отдельный extra, чтобы ядро оставалось «только numpy + Pillow», а MCP-слой подключался
опционально.

> **Оговорка по Python:** актуальный SDK MCP (`mcp`) требует **Python 3.11+**, а
> `pyproject.toml` сейчас декларирует `>=3.10`. Варианты: (а) поднять минимум до
> 3.11, (б) зафиксировать более старую версию SDK, совместимую с 3.10. Решение —
> при реализации, не в этом документе.

### 8.3. Эскиз сервера (SDK v2, `MCPServer`)

```python
# fan_selector/mcp.py  — эскиз, не реализовано
from mcp.server import MCPServer
from fan_selector import run_selection, catalog_lookup, chart_selection

mcp = MCPServer("fan-selector")

@mcp.tool()
def select_fan(q_req: float, p_req: float,
               pressure_type: str = "FULL",
               d_reg_max: float = 1500.0,
               series: list[str] | None = None,
               sizes: list[float] | None = None,
               rpms: list[int] | None = None) -> dict:
    """Подобрать радиальный вентилятор (ВР 86-77 / ВР 280-46) по расходу и давлению."""
    return run_selection({
        "q_req": q_req, "p_req": p_req, "pressure_type": pressure_type,
        "d_reg_max": d_reg_max,
        "series": series or [], "sizes": sizes or [], "rpms": rpms or [],
    })

@mcp.tool()
def lookup_catalog(series: list[str] | None = None,
                   dn: float | None = None,
                   d_over_dn: float | None = None) -> dict:
    """Каталожные карточки: габариты, масса, шум, исполнения, двигатели."""
    return catalog_lookup({"series": series, "dn": dn, "d_over_dn": d_over_dn})

@mcp.tool()
def fan_chart(q_req: float, p_req: float, pressure_type: str = "FULL") -> dict:
    """PNG-график характеристик P(Q) и рабочей точки (base64)."""
    return chart_selection({"q_req": q_req, "p_req": p_req, "pressure_type": pressure_type})

# Ресурсы справочников — по URI fan://data/{fans,impellers,motors,catalog,config}
# и fan://docs/calculation. Читаются из data/*.json напрямую (или через repositories).
```

Запуск:

```bash
# локально, stdio
uv run mcp run fan_selector/mcp.py --transport stdio

# удалённо, Streamable HTTP
uv run mcp run fan_selector/mcp.py --transport streamable-http
```

Регистрация — в MCP-конфиге клиента (например, `claude_desktop_config.json` /
`mcp.json`), с командой запуска `python -m fan_selector.mcp`.

### 8.4. Тесты

Golden-тесты не меняются (они проверяют ядро). Добавляется один smoke-тест,
который поднимает сервер и вызывает `select_fan` через MCP-клиент, сверяя сводку
с эталоном `{'passed': 9, 'best_model': 'ВР 280-46-6.3(1DN)-Y-X/750', ...}`. Принцип
«интерфейс — это тестовая поверхность»: инструмент MCP тестируется ровно тем же
швом, что и реальный клиент. Ручная проверка — `mcp dev` / MCP Inspector.

## 10. Итог одной строкой

Ядро уже является чистым JSON-сервисом; «оформить как MCP» означает добавить
**тонкий MCP-адаптер** (инструменты `select_fan`/`lookup_catalog`/`fan_chart` +
ресурсы `fan://data/*`) и сделать его каноническим контрактом, а навык —
вторичной UX-обёрткой или фолбэком. Полная замена навыка возможна только после
подтверждения, что хост потребляет MCP.
